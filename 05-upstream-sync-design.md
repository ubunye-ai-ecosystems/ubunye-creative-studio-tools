# 05 — Upstream monitoring and synchronisation design

## 1. Constraints from the research

- **Velocity.** Upstream lands about 100–370 commits per day per repo (1,100–1,550 commits in 10 days) and cuts a minor version about every 2 days. [VERIFIED] A daily sync will typically carry 50–300 commits, so per-commit human review is not realistic. The design must summarise and classify.
- **No reliable upstream CI signal.** FilmCraft runs no tests in CI. LightCraft runs them only on FreeBSD. [VERIFIED] So "upstream is green" can't be assumed: we run our own CI on every integration branch.
- **Upstream branches churn.** There are 11–249 remote branches. We track only `main` and tags.

## 2. Flow (runs daily, per app repo)

```
cron 03:17 UTC ──► upstream-sync.yml
   1. fetch upstream main + tags
   2. compare to UPSTREAM_STATE.json.last_integrated.sha
        no new commits ─► record "checked_at", exit
   3. fast-forward origin/upstream-main  (fails loudly if not fast-forwardable: upstream rewrote history)
   4. classify range last..new
        • commits, authors, tags/releases in range
        • conventional prefixes + keywords → features / fixes / breaking / security
        • Cargo.lock diff → dependency bumps; cargo audit on new lockfile
        • paths touched ∩ Ubunye patch set (ubunye/patched-paths.txt) → conflict hotspots
   5. update the rolling branch integration/upstream (created from develop if absent); git merge --no-ff <new sha>
        clean merge ─► push the integration branch
        conflicts   ─► abort the merge (never commit conflict markers); push the integration branch
                       at develop, attach the conflict report (files + hunks), label needs-resolution;
                       a maintainer resolves locally and pushes the merge commit to that branch
   6. open/update PR → develop with summary report (markdown), labels: upstream-sync, risk:<low|med|high>
   7. CI on the PR: cargo xtask ci (Linux/macOS/Windows), cargo deny, cargo audit, brand-leak check,
      smoke tests, wasm build
   8. write the outcome to UPSTREAM_STATE.json *on the integration branch*, so it lands only when a human merges
   9. a human reviewer approves and merges (merge commit). Branch protection enforces approval.
```

Hard rules (enforced by branch protection plus the workflow):
- The bot can **only** fast-forward `upstream-main` and push `integration/*` branches. It has no permission to push `develop`, `release/*` or `main`. We use a GitHub App token scoped to the repo; branch rulesets bypass only `upstream-main` and `integration/**` for that app.
- **No force-push** anywhere. If upstream rewrites history (non-fast-forward), the workflow stops, opens an issue labelled `upstream-history-rewrite`, and changes nothing.
- **No auto-merge.** Integration PRs require one approval from `@ubunye-ai-ecosystems/creative-maintainers`, plus green required checks.
- Upstream changes never deploy anywhere. Release workflows trigger only on `vX.Y.Z-ubunye.N` tags cut from `release/*` (see 06).
- Only one open integration PR per app. If yesterday's PR is still open, the workflow **updates it**: it merges the newer `upstream-main` into the same integration branch, so reviewers don't get seven PRs a week.

## 3. Change classification

Output: a markdown section in the PR body plus a `sync-report.json` artifact.

| Category | Signal |
|---|---|
| Release | new tags in range; upstream `Cargo.toml` `workspace.package.version` change |
| Breaking | `!:` / `BREAKING` in message; MSRV (`rust-version`) change; project-file format version constants changed (`.fcproj`, `.pcraft`, catalog schema); public CLI/MCP command removed (diff of `<app>-cli commands --json`) |
| Security | keywords (`security`, `CVE`, `RUSTSEC`, `overflow`, `panic`, `fuzz`, `sanitize`, `untrusted`); `cargo audit` delta (new or fixed advisories); changes in parser crates (`crates/{raw,tiff,psd,isobmff,matroska,…}`) |
| Features / Fixes | `feat`/`fix` prefixes, or upstream task-id conventions (one task id per commit) |
| Dependencies | `Cargo.lock` package adds, removes and version changes; new `-sys`/`build.rs` crates; new git deps (fails policy) |
| Branding drift | new occurrences of `ArtCraft`, `getartcraft`, `ai.storyteller`, `Learning Machines`, `storytold` outside allow-listed files (NOTICE, LICENSE*, ATTRIBUTION*, credits) |
| Conflict hotspots | files touched by upstream that also appear in `git diff upstream-main...develop --name-only` |

The summary is generated by a deterministic script (`scripts/upstream_report.py`, which lives in `ubunye-creative-studio` and is called from a reusable workflow). An LLM step for a prose summary is optional, kept off by default, and must never decide merges.

## 4. `UPSTREAM_STATE.json`

Schema and example: [`templates/UPSTREAM_STATE.json`](templates/UPSTREAM_STATE.json). Key fields:
- `upstream.url`, `upstream.branch`
- `last_checked_at`
- `last_integrated`: `{sha, date, upstream_version, merged_pr, merged_by, merged_at}`
- `pending`: `{sha, integration_branch, pr, status: clean|conflicts|ci_failed, report}`
- `history[]`: the last N integration outcomes

## 5. Conflict-minimisation (what makes this sustainable)

1. **Brand layer instead of global renames.** All identity strings come from one `ubunye-brand` source (see `REBRANDING.md`). Upstream files get a minimal hook such as `brand::APP_NAME`, not 1,200 edits. Locale catalogs: override through an **overlay catalog** loaded after upstream's, instead of editing upstream's `.ftl`/`.json` files. This needs a small upstreamable patch to the i18n loader.
2. **Packaging overrides** live in `ubunye/packaging/`, and our release workflow calls them. Upstream `packaging/` is left untouched where possible.
3. **Our CI workflows** are named `ubunye-*.yml`, so they never collide with upstream workflow files. Upstream workflows that would publish under upstream identities (`release.yml`) are disabled with `if: github.repository_owner == 'storytold'`. Better still, propose that guard upstream; otherwise patch it once.
4. **Upstream contributions.** Offer upstream the generic hooks (brand indirection, workflow owner guard, i18n overlay). Every accepted hook shrinks our permanent diff.

## 7. Verification

On 2026-10-10 the workflow's `run:` steps ran locally with a minimal runner. Inputs: a bare `origin` (fork imported at LightCraft `5c1dcd4`, one day behind) and the real upstream history up to `b70ae17` (524 commits). `gh` was stubbed.

| Scenario | Expected | Result |
|---|---|---|
| Clean merge | `upstream-main` fast-forwarded; merge commit on `integration/upstream` with parents (develop, upstream); `UPSTREAM_STATE.json.pending.status = clean` only on the integration branch; `develop` untouched; PR created with the report | ✅ |
| Conflict (Ubunye edited a README line that upstream also changed) | merge aborted (no conflict markers committed); conflict list appended to the PR; `pending.status = conflicts`; `README.md` listed as a hotspot | ✅ |
| Upstream history rewrite (`last_integrated` not an ancestor) | issue opened, job fails, nothing pushed | ✅ |
| Rerun in the same workspace | idempotent remote setup | ✅ after fix |

Report quality on real data (last 24 hours of each upstream): Light 380 commits (v0.4.0 → v0.5.0, 1 possibly-breaking catalog format bump, 5 security-relevant); Photo 341 (v0.5.0 → v0.6.0); Film 231 (v0.4.0 → v0.5.0). Upstream task-ID prefixes (`LR-IMP-FORMATS:` and so on) are grouped as "commits by area".
